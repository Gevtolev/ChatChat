## 一、目标

让编译出来的 wiki **可导航、可发现**。

前两个子项目让知识进得来、编得成；这一个决定用户是否愿意回来看。调研中反复出现的失败模式是"笔记堆积但找不到、用不上"，本子项目正对着这一条。

## 二、轻量图谱

### 2.1 为什么"轻量"是可行的

`nashsu/llm_wiki` 用了 4 个关联信号，其中**三个只需要页面元数据**，不需要向量、不需要图数据库：

| 信号 | 数据来源 | 计算 |
|---|---|---|
| **直接链接** | 页面的 `links[]` | 直接读 |
| **来源重叠** | 页面的 `sources[]` 交集 | 集合运算 |
| **类型亲和** | 页面的 `type` + `tags` | 直接比 |
| Adamic-Adar | 共同邻居的加权 | 纯 JS 几十行 |

子项目二的页面结构里 `links` / `sources` / `type` / `tags` **全都有**，图谱是纯查询 + 纯计算，零额外存储、零 LLM 调用、零新增依赖。

### 2.2 本子项目做什么

- 节点 = wiki 页面，边 = 直接链接（一期只用最强的那个信号）
- 按 `type` 着色，按入链数定大小
- 点击节点跳转页面
- **不引入图表库** —— 与成本看板同样的判断，内联 SVG 力导向布局，避免为一个功能引入数百 KB 依赖

### 2.3 明确推迟

- **Louvain 社区检测**（自动发现知识簇）—— 有价值但复杂，等图谱有真实规模再说
- **Graph Insights**（意外关联 / 知识缺口发现）—— `llm_wiki` 最有意思的能力，但需要前述聚类做基础
- 后三个关联信号 —— 先看直接链接够不够用

## 三、浏览

- **wiki 页面阅读** —— markdown 渲染，`[[wikilink]]` 可点击跳转
- **索引视图** —— 按 `type` 分区（entity / concept / comparison / query / summary），每条一行摘要，对应 skill 里的 `index.md`
- **溯源** —— 页面上显示 `sources`，可跳回原始文件；`^[source]` 段落级溯源标记若已生成则渲染
- **全文搜索** —— Mongo 文本索引，跨页面标题与正文

## 四、lint 报告

skill 定义的 lint 有多项，本子项目**只做不需要 LLM 的四项**（纯查询，成本为零）：

| 检查 | 实现 |
|---|---|
| 孤立页 | 无入链的页面 |
| 断链 | `links[]` 指向不存在的 slug |
| 待拆页 | 正文超过约 200 行 |
| 重复标题 | 同名或高度相似的标题 |

外加两项直接读字段的：`contested: true` 的页面、`confidence: low` 的页面 —— 这是 skill 里"防止弱证据固化成事实"的机制，展示成本为零。

**明确不做**：语义级的事实矛盾检测。那需要 LLM 逐页比对，成本随知识库规模平方增长。等有真实数据、知道矛盾实际有多普遍再决定。

## 五、待细化（子项目二完成后）

- 图谱在页面数很多时的性能与降级（是否需要按文件夹/标签过滤后再渲染）
- lint 的触发方式（手动按钮 vs 每次摄入后自动）
- 搜索是否需要独立索引服务（Meilisearch 生产未部署，`MEILI_HOST` 未设置）
- 页面能否人工编辑 —— 若可编辑，需处理"人工修改被下次编译覆盖"的冲突

最后一条是真正的开放问题：Karpathy 的模式里 wiki 层是 **agent 所有**的，人不直接改。但产品上用户大概率想改。这个张力需要在实施前想清楚。

---

## 六、明确不做

- 图表库依赖
- 社区检测与缺口发现（推迟，非放弃）
- 语义矛盾检测
- 导出为 markdown 文件包 —— 有价值（对应"你拥有的纯 markdown"理念），但属独立议题，不占用本子项目预算
